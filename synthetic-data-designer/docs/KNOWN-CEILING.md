# The known ceiling

How to measure a model against the best score anything could achieve, and why that
is a different kind of claim from "our synthetic data is realistic".

## The problem it solves

A credit model scores 0.84 on a lender's book. Is that good?

You cannot tell. The data has a ceiling — some borrowers default for reasons nothing
in the file predicts — and on real data that ceiling is unobservable. So every
comparison of model quality is a comparison of numerators over an unknown
denominator, and every disagreement about whether a model is good enough is
unresolvable in principle.

The usual response is to argue about realism instead: *is the synthetic data close
enough to the real thing?* That argument never ends, because "close enough" has no
threshold and the person who wants to reject the data can always find a marginal
they dislike.

**Reframe it.** Stop claiming the data is realistic. Claim something checkable: the
data was generated by a process you declared, so the best achievable score on it is
computable. Now 0.84 has a denominator.

## The two numbers

| | what it answers |
|---|---|
| **Ceiling** | the best score obtainable from the columns a model is allowed to see |
| **Oracle** | what a model that could see the hidden driver would score |

The **ceiling** is the honest target. The **oracle** is an absolute upper bound, and
the distance between them is information the observables simply do not carry —
no model closes that gap, however good.

That distance is itself useful: it separates *"buy a better model"* from *"buy better
data"*, which is usually the more expensive question to get wrong.

## How it works

Each entity gets a hidden driver — in the shipped pack, `risk_tier` A through E —
that determines how fast it deteriorates. The driver is a `helper` column, so it is
generated, used, and **dropped before the output is written**. A model must infer it
from observables that are noisy readings of it.

Because the emission model is declared — each observable is its tier's centre plus
independent noise of stated width — the posterior over the hidden tier given the
observables is exact. Bayes' rule, not simulation:

```
P(tier | observables) ∝ P(tier) · Π  Normal(observable ; centre[tier], width)
best possible score    =  E[ P(bad | tier) | observables ]
```

`P(bad | tier)` is measured by generating once with the driver exposed — using the
ageing engine itself as the source of truth rather than re-deriving the outcome from
the transition matrix, which would be a second implementation of the same thing and
would eventually disagree with the first.

Being **derived rather than estimated** is the point. An approximated ceiling is one
more number to argue about, and the purpose here is to end an argument.

## Using it

```python
import pandas as pd
from sdd import api, benchmark

spec = api.load("credit_benchmark_known_ceiling")
panel = pd.read_parquet(api.run(spec, 20_000, "./out", seed=7)["panel"])

known = benchmark.ceiling(spec, panel)
print(known.summary())
# ceiling 0.8987 · oracle 0.9162 (observables cost 0.0175) · outcome rate 12.912%

benchmark.compare(spec, panel, my_scores, name="challenger")
# {'achieved': 0.8923, 'ceiling': 0.8987, 'captured': 0.984,
#  'gap_to_ceiling': 0.0064, 'beat_the_ceiling': False, ...}
```

`captured` is the number worth quoting: the share of *available* signal the model
found, where available means above a coin flip and up to the ceiling. Unlike raw AUC
it is comparable across datasets.

**Score out of sample.** The ceiling is a population quantity; an in-sample score is
not comparable to it.

## The check that keeps it honest

A ceiling is a claim, and a claim that cannot fail is worth nothing. So `compare()`
reports `beat_the_ceiling`, because a model **cannot** legitimately exceed the best
achievable score. If one does, either the ceiling is wrong or the model saw something
it should not have.

It caught a real mistake during development: a gradient booster fitted and scored on
the same rows reached **0.93** against a ceiling of **0.897**. Not a strong model — a
memorised one. On a real portfolio that result is indistinguishable from success.

## The difficulty dial

The noise widths in the pack decide how much the observables reveal:

| noise | ceiling | oracle | cost of the observables |
|---|---:|---:|---:|
| 0.5× | 0.9158 | 0.9162 | 0.0004 |
| 1.0× | 0.9015 | 0.9162 | 0.0147 |
| 2.0× | 0.8476 | 0.9162 | 0.0686 |

The oracle barely moves — the hidden driver is unchanged. The ceiling moves a lot.

This is what makes it an *instrument* rather than a dataset: you can manufacture a
problem of **known difficulty** and check that an evaluation pipeline reports that
difficulty correctly. A validation process that cannot tell an easy problem from a
hard one will not tell you much about a real one.

## Declaring your own

Any pack becomes an instrument by adding a `benchmark` block naming the hidden
driver, the observables and what counts as a bad outcome:

```yaml
benchmark:
  latent: risk_tier          # must be role `helper`, so it never reaches the output
  observables:
    - {column: bureau_score, centres: _centre_score, noise: _noise_score}
    - {column: revolving_utilisation_pct, centres: _centre_util, noise: _noise_util}
  label_states: ["60-89 DPD", Defaulted]
```

Three requirements, and they are real restrictions rather than conventions:

1. **The driver must be hidden** (`role: helper`). A driver a model can read is not
   hidden, and the ceiling would be meaningless. This is enforced.
2. **Each observable is a centre plus independent Gaussian noise**, both declared.
   That is what makes the posterior exact. A generating process that cannot be
   written down cannot be inverted.
3. **The measurement errors must be independent of each other.** That independence is
   what makes combining observables worth more than reading the best one, and it is
   what puts the ceiling above any single feature.

## Honest limits

**A good score here does not mean a model will work on a real book.** This data was
made by rules we wrote. A model that excels at recovering them has recovered our
rules, and nothing else.

What transfers is narrower and still worth having: whether a model extracts the
signal that is present, and whether an evaluation process is sound. Predicted
performance does not transfer — for that, point the same pipeline at a real tape,
which the profiler makes a one-file change.

**The ceiling is exact for this generating process, not for credit in general.** It
says what was achievable *here*.
